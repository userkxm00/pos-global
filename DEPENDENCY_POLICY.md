# Dependency and Lockfile Policy

## Purpose

Keep dependency changes reviewable, reproducible and security-auditable without blocking the Foundation on fabricated lockfiles.

## Rules

1. Do not add a dependency casually.
2. Every dependency addition requires a documented reason, alternatives review, security/license review and build/test impact review.
3. Production/release builds must use committed lockfiles (`package-lock.json` and `src-tauri/Cargo.lock`) and CI must use locked installation/resolution.
4. Lockfiles must be generated by the real build environment and committed as normal repository files. Never hand-invent or copy lockfile contents from an unrelated environment.
5. A missing lockfile is a reproducibility blocker for `PRODUCTION_READY` and release gating.
6. Dependency advisories must have explicit disposition. High/critical findings may not be hidden by `continue-on-error` or ignored without a documented reason and mitigation plan.
7. Dependabot remains enabled for dependency update visibility.
8. Before production, run a complete dependency review covering npm, Cargo and GitHub Actions dependencies.

## Foundation interpretation

The Foundation Gate verifies that the current dependency audit command succeeds and that security findings are visible. The absence of committed lockfiles does not by itself make the architecture invalid, but it prevents `PRODUCTION_READY` and release approval until the required lockfiles are generated and verified.

## Agent rule

An agent may not fabricate a lockfile. When a lockfile is required, it must be generated by the project's actual package manager/toolchain and verified by CI.
